# Model Card: N-BEATS для прогнозирования ежедневных продаж

Документ ДЗ №2 по предмету «Бизнес-применение машинного обучения».
Дата составления: 5 ноября 2026 года. Состояние кода: `main`, коммит `37a2719`.
Структура следует разделам Google
[Model Cards for Model Reporting](https://research.google/pubs/model-cards-for-model-reporting/).
Факты о модели и результатах взяты из файлов проекта, перечисленных ниже.
Предполагаемое использование и потенциальные риски обозначены отдельно.

**Статус:** исследовательская реализация и ограниченный эксперимент, а не
подтверждённая производственная модель. Эксперимент N-BEATS с пятью шагами
обучения проведён только на трёх рядах `1/1`, `1/2`, `1/3` и не доказывает
качество модели на всём датасете из 500 рядов.

### Архитектура

Используется N-BEATS из NeuralForecast. Для основной конфигурации обвязка
сохраняет архитектурные параметры библиотеки по умолчанию. В отчёте реального
эксперимента зафиксированы стеки `identity`, `trend`, `seasonality`, по одному
блоку в каждом и полносвязные слои `512/512`. Один объект модели обучается на
переданных временных рядах вместе; отдельный экземпляр для каждой пары не создаётся.

Входное окно — 180 ежедневных наблюдений, выходной горизонт — 90 дней.
Дополнительные признаки, цены, промоакции, остатки и сведения о поставках
в обвязку не передаются. `unique_id` обозначает ряд, `ds` — временную ось;
их нельзя трактовать как явно добавленные числовые признаки модели.

### Конфигурации и обучение

| Параметр | Основной эксперимент | Реальный ограниченный запуск |
| --- | --- | --- |
| `h` | 90 | 90 |
| `input_size` | 180 | 180 |
| `max_steps` | 500 | 5 |
| `learning_rate` | 0.001 | 0.001 |
| `batch_size` | 32 | 32 |
| `scaler_type` | `standard` | `standard` |
| `random_seed` | 42 | 42 |
| Архитектура | Стандартная архитектура Nixtla | Та же, `smoke=False` |

`EXPERIMENT_CONFIG` неизменяемый. Реальный сценарий создаёт его копию с пятью
шагами; основной запуск на 500 рядах с 500 шагами не выполнялся. `FAST_CONFIG`
существует отдельно: два шага, один identity-блок и слои `32/32`; это техническая
проверка, результаты которой не подменяют реальный эксперимент.

`fit_nbeats` получает только Train в формате `unique_id`, `ds`, `y` и вызывает
`NeuralForecast.fit(..., val_size=0)`. Внутренний holdout и early stopping
не используются; Validation оценивается отдельно. Искусственное дополнение
истории нулями отключено. Требуется минимум 270 непрерывных дней Train
(`180 + 90`) для каждого ряда. Нормализация применяется внутри модели к данным
обучения; будущие фактические продажи в функцию прогнозирования не передаются.

## 2. Intended Use — назначение и предполагаемое использование

**Реализованное назначение:** получить прогноз количества ежедневных продаж
для каждой пары магазин–товар на следующие 90 дней и сравнить его с фактическими
продажами на отложенном периоде. Это учебный проект с экспериментальной оценкой.

**Предполагаемая бизнес-задача:** дать специалисту по запасам ориентир ожидаемых
продаж при планировании пополнения. Возможный пользователь — аналитик или
планировщик, который проверяет прогноз и учитывает другие ограничения бизнеса.
Такое применение пока не реализовано и не проверено на бизнес-показателях.

ML рассматривается как способ обучаться на исторических временных зависимостях;
в проекте возможность проверяется сравнением с простым недельным Seasonal Naive.
Доказательств, что ML необходим или экономически выгоднее baseline в реальном
процессе, пока нет. Снижение ошибки прогноза само по себе не доказывает рост прибыли.

Не подтверждены автоматическое размещение заказов, работа в реальном времени,
использование на новых магазинах/товарах без истории и перенос на другие рынки.
Эта карточка не является разрешением на автономное управление закупками.

### Вход и выход

| Этап | Данные и проверки |
| --- | --- |
| Источник | CSV с `store`, `item`, `date`, `sales`; локальная копия `data/raw/train.csv` исключена из Git |
| Подготовка | `unique_id` — экранированная пара `store/item`; `ds` — дата; `y` — продажи |
| Требования | Непустая таблица, обязательные колонки, отсутствие пропусков и дубликатов; корректные даты без времени и часового пояса; конечные неотрицательные продажи |
| Временная история | Ежедневные непрерывные даты; для общего разделения все ряды должны завершаться одной датой |
| Прогноз | `unique_id`, `ds`, `y_pred`: ровно 90 будущих дат каждого обученного ряда |
| Контроль результата | Пропуски, лишние ключи, дубликаты и неконечные прогнозы вызывают ошибку; порядок строк не влияет на сопоставление |

Прогноз может быть дробным или отрицательным: текущая обвязка не округляет и
не обрезает значения. Он не является готовым количеством единиц к заказу.

## 3. Factors — факторы применимости и оценки

В проекте различаются магазин, товар, календарный период и длина истории ряда.
Недельная структура продаж отражена в baseline с периодом 7 дней. Для N-BEATS
оценивается общий результат только трёх заранее заданных рядов одного магазина.

Отдельные показатели по всем магазинам, товарам, уровням продаж, сезонам
и их пересечениям не приведены. Устойчивость к смене ассортимента, промоакциям,
дефициту товара и изменению режима продаж не измерена. Это потенциальные факторы
переноса в бизнес, а не установленные причины ошибок в проведённом запуске.

## 4. Metrics — метрики

Источник: [metrics.py](src/sales_forecasting/metrics.py) и
[evaluation.py](src/sales_forecasting/evaluation.py).

| Метрика | Расчёт | Смысл |
| --- | --- | --- |
| MAE | `mean(abs(y - y_pred))` | Средняя абсолютная ошибка в единицах продаж |
| RMSE | `sqrt(mean((y - y_pred) ** 2))` | Ошибка в единицах продаж с большим влиянием крупных промахов |
| MAPE | `100 * mean(abs((y - y_pred) / y))` при `y != 0` | Средняя абсолютная процентная ошибка |

Для всех метрик меньше — лучше. Каждое наблюдение имеет равный вес;
отдельного усреднения метрик по рядам нет. MAPE исключает строки с нулевым фактом;
если весь факт нулевой, `mape` и общий оценщик вызывают `ValueError`.
MAE и RMSE учитывают нули. Поэтому MAPE не характеризует ошибки на днях без продаж.

Перед расчётом требуется точное совпадение ключей `(unique_id, ds)` между фактом
и прогнозом. Пропущенные, лишние и дублирующиеся прогнозы отклоняются.
Бизнес-порог приемлемого качества, стоимость дефицита/излишков и экономические
метрики в проекте не определены.

## 6. Training Data — обучающие данные

Реальный запуск N-BEATS использовал только 4938 строк Train выбранных трёх рядов:
по 1646 ежедневных наблюдений на ряд, до 2017-07-04 включительно.
Это не обучение на всех 823 000 строках Train всей панели. Внешние признаки
и дополнительные наборы данных в описанный запуск не включались.

[splitting.py](src/sales_forecasting/splitting.py) проверяет общие границы,
достаточность истории и отсутствие пересечений. Вызывающий код обязан передать
именно Train: `fit_nbeats` не может распознать ошибочную передачу всего CSV.
В [real_data_experiment.py](src/sales_forecasting/real_data_experiment.py)
разделение выполняется до обучения, а Test не передаётся модели или оценщику.

## 7. Quantitative Analyses — количественные результаты

Подтверждённые результаты на Validation из [отчёта](docs/experiments/real_sales.md):

| Область | Модель | MAE | RMSE | MAPE, % |
| --- | --- | --- | --- | --- |
| Все 500 рядов | Seasonal Naive, период 7 | 11.591733 | 15.179079 | 20.258857 |
| Только `1/1`, `1/2`, `1/3` | Seasonal Naive, период 7 | 8.259259 | 11.086528 | 22.529076 |
| Те же три ряда | N-BEATS, 5 шагов | 7.672950 | 10.337319 | 17.834546 |

Сравнивать методы напрямую можно только по двум последним строкам.
В одном ограниченном запуске N-BEATS получил меньшие ошибки; это не доказывает
превосходство на других рядах, устойчивость по времени или сходимость обучения.
Не представлены доверительные интервалы, повторения с разными seed,
скользящая проверка и разбивка качества по группам.

Время: полный baseline pipeline — 20.845 с; N-BEATS `fit` — 1.717 с,
создание модели/первый импорт и `fit` — 13.907 с, прогноз и оценка — 0.105 с.
Проверено 270 прогнозных строк, по 90 будущих дат каждого ряда, без дубликатов
и пропущенных ключей. Разные интервалы включают разные операции и не дают
корректного сравнения скорости моделей.

## 8. Ethical Considerations — риски и ответственность

Ниже перечислены **потенциальные риски предполагаемого применения**;
их вероятность и экономический эффект в проекте не измерялись.

- Занижение прогноза может привести к недостаточным запасам, завышение —
  к излишкам. Автоматическое исполнение закупок без проверки не реализовано.
- Зарегистрированные продажи не гарантируют измерение полного спроса:
  при отсутствии товара продажи могут быть ограничены наличием. Остатки
  и неудовлетворённый спрос не входят в используемую схему.
- Выводы по одному магазину и трём товарам могут не переноситься на остальные
  группы. Отдельная проверка равномерности качества по магазинам не проведена.
- Во входной схеме нет персональных признаков покупателей; это не является
  результатом аудита приватности или лицензирования исходных данных.
- Пользователю необходимо видеть границы эксперимента и отличать точечный прогноз
  от достоверного обещания продаж. Интервалы неопределённости не реализованы.

Для будущего бизнеса предполагается проверка аналитиком/планировщиком;
процедура согласования решений и назначенные ответственные пока не реализованы.

## 9. Caveats and Recommendations — ограничения и дальнейшие шаги

Основные ограничения: пять шагов на трёх рядах, один период Validation,
отсутствие Test-метрик, полного обучения, оценки экономического эффекта,
производственного развёртывания и мониторинга дрейфа. Короткие и разрывные
ряды отклоняются; прогноз может быть отрицательным и дробным. Seed фиксирован,
но переносимость результатов между окружениями не доказана.

**Предлагаемые дальнейшие шаги, не выполненные в этом проекте:** расширить
оценку по заранее определённым группам, проверить устойчивость на нескольких
временных окнах, определить бизнес-критерии, после выбора модели провести
отдельную итоговую оценку на Test. Для планирования запасов дополнительно нужны
остатки, сроки поставки, ограничения заказа и правила обработки прогноза.

`pipeline.py` реализует сквозной сценарий baseline. N-BEATS подключён отдельными
функциями и ограниченным экспериментом; промышленный процесс пополнения запасов
не реализован. Его предполагаемая схема приведена в [Model_BPMN.md](Model_BPMN.md).
