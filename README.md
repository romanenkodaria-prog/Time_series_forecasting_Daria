# Time_series_forecasting_Daria

Учебный проект: прогноз ежедневных продаж по парам магазин–товар на 90 дней.
Реализованы загрузка CSV, валидация, подготовка и хронологическое разделение
данных на pandas, Seasonal Naive baseline и оценка качества прогнозов.
Сквозной pipeline оценивает baseline только на Validation. Добавлена обвязка
N-BEATS через Nixtla NeuralForecast с отдельным синтетическим пробным запуском.
Исходное исследование: [Time_series_forecasting](https://github.com/Evgeniy-hub-star/Time_series_forecasting).

## Использование

Пример `data/sales.csv`:

```csv
store,item,date,sales
1,3,2024-01-02,5
1,3,2024-01-01,0
2,4,2024-01-01,8
```

Сохраните код в `example.py` и запустите `poetry run python example.py`:

```python
from sales_forecasting.data import load_sales_csv
from sales_forecasting.preprocessing import prepare_sales_data
from sales_forecasting.validation import (
    validate_forecasting_data,
    validate_raw_data,
)

raw = load_sales_csv("data/sales.csv")  # Чтение и проверка исходной схемы
validate_raw_data(raw)  # Также подходит для DataFrame из другого источника
prepared = prepare_sales_data(raw)
validate_forecasting_data(prepared)
print(prepared)
```

Результат отсортирован по `unique_id`, `ds`:

```text
  unique_id         ds  y
0       1/3 2024-01-01  0
1       1/3 2024-01-02  5
2       2/4 2024-01-01  8
```

`unique_id` строится как `store/item`: компоненты экранируются URL-кодированием,
чтобы разделители внутри идентификаторов не создавали коллизий. При чтении CSV
ведущие нули в `store` и `item` сохраняются. `ds` — pandas datetime,
`y` — числовая колонка. Исходная таблица не изменяется. Дополнительные колонки
допускаются, но в результат не попадают.

Валидация отклоняет пустые таблицы, отсутствующие и повторяющиеся колонки,
пропуски (включая пустые строки), некорректные даты, отрицательные,
нечисловые и бесконечные продажи, дубликаты `(unique_id, ds)`.
Даты принимаются в формате `YYYY-MM-DD` или как pandas datetime без часового
пояса и времени суток. Нулевые и дробные продажи допускаются.
Пропущенные дни не заполняются, дубликаты не агрегируются.

Ошибки данных вызывают `ValueError`, неверный тип таблицы — `TypeError`.
`load_sales_csv(path, encoding="utf-8")` читает CSV с запятой как разделителем.
Отсутствующий файл вызывает `FileNotFoundError`, проблемы доступа — `OSError`,
ошибки CSV или кодировки — `ValueError`. Сообщения содержат путь к файлу.

## Train, Validation и Test

`split_series(prepared)` возвращает три независимые таблицы:

- **Train** — данные до начала Validation, для обучения модели.
- **Validation** — следующие 90 календарных дней, для сравнения моделей
  и настройки гиперпараметров.
- **Test** — последние 90 календарных дней, для итоговой оценки после выбора
  модели. Test нельзя использовать для подбора модели или параметров.

Границы общие для всех рядов и отсчитываются от максимальной даты всей таблицы.
Train строго предшествует Validation, а Validation — Test, в том числе между
разными рядами. Случайное перемешивание при разделении не применяется.
Преобразования, которым нужно обучение (например, масштабирование), следует
обучать только на Train; функция разделения таких преобразований не выполняет.

Каждый ряд должен иметь непрерывную ежедневную историю до общей конечной даты.
По умолчанию нужны хотя бы 181 день: один день Train и по 90 дней двух следующих
периодов. Для будущей модели задайте достаточный `min_train_days`, исходя из её
окна обучения. Ряды с пропущенными днями, более ранней конечной датой или короткой
историей отклоняются с указанием идентификатора; данные не дополняются автоматически.
Разная начальная дата рядов допускается. `validation_days` и `test_days` можно
изменить явно; все три параметра длины должны быть положительными целыми числами.

```python
from sales_forecasting.splitting import split_series, validate_splits

train, validation, test = split_series(prepared, min_train_days=180)
validate_splits(train, validation, test)
```

Для этого примера каждому ряду нужны минимум 360 ежедневных наблюдений.
`validate_splits` также позволяет проверить самостоятельно сформированные разделы:
он требует одинаковый набор рядов и строгий порядок непересекающихся периодов
во всей панели. Длительность и непрерывность окон контролирует `split_series`.
Исходная таблица не изменяется, результат сортируется по `unique_id`, `ds`.

## Оценка качества

Прогнозная таблица должна содержать `unique_id`, `ds`, `y_pred`.
`align_forecasts(actual, forecasts)` возвращает `unique_id`, `ds`, `y`, `y_pred`.
Сопоставление строгое по `(unique_id, ds)`: требуются ровно те же ключи, что
в фактической таблице. Пропущенные и лишние ключи, дубликаты с любой стороны,
пропуски и неконечные прогнозы вызывают `ValueError`. Порядок строк и индексы
не влияют на результат. Даты нормализуются, идентификаторы приводятся к строкам.
Отрицательные прогнозы допускаются и оцениваются без обрезки.

```python
from sales_forecasting.evaluation import evaluate_forecasts

# forecast_validation — прогноз выбранной модели на Validation,
# полученный отдельно; функции оценки сами прогнозы не создают.
scores = evaluate_forecasts(validation, forecast_validation)
print(scores)  # {"MAE": ..., "RMSE": ..., "MAPE": ...}
# Test оценивается отдельно только после окончательного выбора модели.
```

Для факта `y` и прогноза `p`:

| Метрика | Формула | Интерпретация |
| --- | --- | --- |
| MAE | `mean(abs(y - p))` | Средняя абсолютная ошибка в единицах продаж |
| RMSE | `sqrt(mean((y - p) ** 2))` | Ошибка в единицах продаж, сильнее учитывает крупные промахи |
| MAPE | `100 * mean(abs((y - p) / y))`, только `y != 0` | Средняя абсолютная процентная ошибка |

Чем меньше значение, тем лучше. Метрики рассчитываются по всем строкам вместе,
с равным весом каждого наблюдения, без отдельного усреднения по рядам.

**Политика нулей MAPE:** строки с нулевым фактом исключаются только из MAPE.
Если весь факт нулевой, `mape` и `evaluate_forecasts` вызывают `ValueError`,
поскольку процентная ошибка не определена. MAE и RMSE учитывают нули и остаются
доступны отдельно. MAPE может скрывать ошибки на днях без продаж, поэтому
рассматривайте её вместе с MAE и RMSE; малые ненулевые продажи могут давать
очень большие проценты.

```python
from sales_forecasting.metrics import mae, rmse, mape

print(mae([0, 10, 20], [3, 12, 16]))  # 3.0
print(rmse([0, 10, 20], [3, 12, 16]))  # около 3.109
print(mape([0, 10, 20], [3, 12, 16]))  # 20.0 (%)
```

Отдельные функции метрик сопоставляют значения по позиции, а не по индексам
pandas. Они требуют непустые одномерные последовательности одинаковой длины
с конечными числами. Для таблиц используйте `evaluate_forecasts`, чтобы сначала
проверить соответствие ключей.

## Seasonal Naive baseline

Модель повторяет последние семь ежедневных наблюдений Train: для шагов 1–7
используется последняя неделя, для шагов 8–14 — та же неделя и так далее.
Период сезонности фиксирован: **7 дней**. Прогноз по умолчанию — **90 дней**.
Первый прогнозный день следует сразу за последней датой истории каждого ряда.
Validation не используется для обновления недельного шаблона.

```python
from sales_forecasting.models.baseline import seasonal_naive

validation_forecasts = seasonal_naive(train)
```

Результат содержит `unique_id`, `ds`, `y_pred`. Модель проверяет исходную схему
существующим валидатором, сортирует историю, требует минимум семь наблюдений
в каждом ряду и непрерывные ежедневные даты во всей переданной истории.
Недостаточная история и пропущенные даты вызывают `ValueError` с идентификатором
ряда. Пропуски не заполняются. Исходная таблица не изменяется. Нулевые продажи
допускаются. При отдельном вызове доступен параметр `horizon`, например
`seasonal_naive(train, horizon=14)`; это положительное целое число.

### Сквозной запуск

Подготовьте локальный CSV с колонками `store,item,date,sales`. Каждый ряд должен
содержать минимум **187 последовательных дней**: семь дней Train, 90 Validation
и 90 Test. Конечная дата должна совпадать у всех рядов.
Короткий CSV из раздела «Использование» подходит только для подготовки данных.

```powershell
poetry run python -m sales_forecasting.pipeline data/sales.csv
```

Команда выводит JSON с MAE, RMSE и MAPE **на Validation**. При необходимости
кодировку можно указать через `--encoding utf-8`. Ошибки входных данных выводятся
с понятным сообщением и кодом завершения 2. Никакие файлы результатов не создаются.

Для запуска из Python:

```python
from sales_forecasting.pipeline import run_baseline_pipeline

result = run_baseline_pipeline("data/sales.csv")
print(result.validation_metrics)
print(result.validation_forecasts.head())
# result.train, result.validation и result.test — отдельные таблицы разделов.
```

Pipeline использует существующие загрузчик, подготовку, разделение и оценку:
CSV → подготовленные данные → Train / Validation / Test → прогноз из Train →
строгое сопоставление с Validation → метрики. Проверки и расчёты метрик
переиспользуются, включая сопоставление по ключам `(unique_id, ds)`.
Test участвует только в исходной проверке и выделении разделов: он возвращается
без изменений, не передаётся модели или оценщику и не используется для подбора.
Прогнозы и метрики на Test не вычисляются.

Сохраняется политика MAPE: отдельные нулевые фактические значения исключаются
только из MAPE. Если вся Validation нулевая, pipeline вызывает `ValueError`;
MAE и RMSE в таком случае можно рассчитать отдельно существующими функциями.
Тесты проверяют независимость прогноза от значений Validation и Test.

## N-BEATS через NeuralForecast

Python 3.11 поддерживается NeuralForecast и PyTorch. Для Windows нужен 64-битный
Python; проверено наличие официального PyTorch wheel для Python 3.11 / Windows x64.
Источники: [установка PyTorch](https://pytorch.org/get-started/locally/),
[NeuralForecast на PyPI](https://pypi.org/project/neuralforecast/),
[параметры NBEATS](https://nixtlaverse.nixtla.io/neuralforecast/models.nbeats.html).
Установка проекта: `poetry install --with dev`; используйте `poetry.lock`.
Зафиксированы NeuralForecast **3.3.0** и PyTorch **2.9.1**. В проверяемом окружении
установлена сборка PyTorch **2.9.1+cpu**, PyTorch Lightning **2.6.6**, pandas
**2.3.3**, Python **3.11.9**, Windows x64. CUDA недоступна.
Обвязка явно выбирает CPU и `num_workers=0`, не требует CUDA и не создаёт
процессов загрузки данных, checkpoints или журналов Lightning.

### Конфигурации

`EXPERIMENT_CONFIG` — неизменяемая основная конфигурация:

| Параметр | Значение |
| --- | --- |
| h | 90 |
| input_size | 180 |
| max_steps | 500 |
| learning_rate | 0.001 |
| batch_size | 32 |
| scaler_type | standard |
| random_seed | 42 |

Архитектура основного эксперимента использует значения по умолчанию Nixtla.
`FAST_CONFIG` — отдельная техническая проверка: два шага, один identity-блок,
два слоя по 32 нейрона и 16 обучающих окон в пакете. Горизонт 90 и окно 180,
learning rate, batch size, scaler и seed сохраняются. Параметры основного
эксперимента при этом не меняются. Оценивать качество модели по двум шагам нельзя.

### Использование функций

```python
from sales_forecasting.data import load_sales_csv
from sales_forecasting.evaluation import evaluate_forecasts
from sales_forecasting.models.nbeats import FAST_CONFIG, fit_nbeats, predict_nbeats
from sales_forecasting.preprocessing import prepare_sales_data
from sales_forecasting.splitting import split_series

prepared = prepare_sales_data(load_sales_csv("data/sales.csv"))
train, validation, test = split_series(prepared, min_train_days=270)
fitted = fit_nbeats(train, FAST_CONFIG)
forecast = predict_nbeats(fitted)
print(evaluate_forecasts(validation, forecast))
```

Данные имеют формат `unique_id`, `ds`, `y`. Нужны минимум 270 непрерывных дней
Train на каждый ряд для полного окна `180 + 90` без дополнения нулями; вместе
с двумя отложенными периодами — минимум 450 дней. `create_nbeats(config)`
создаёт необученный объект NeuralForecast. `fit_nbeats(train, config)` возвращает
`FittedNBEATS` с моделью, будущими ключами и временем `fit_seconds`;
внутри используется `val_size=0`, без early stopping. Только
переданный Train участвует в обучении и нормализации; разделять исходную таблицу
нужно до вызова. Обвязка не может определить, передал ли вызывающий код весь CSV
вместо Train. Validation применяется отдельно для оценки, Test — для финальной
проверки только после выбора модели.

`predict_nbeats(fitted)` не принимает будущих фактических значений. Он возвращает
`unique_id`, `ds`, `y_pred`: ровно 90 следующих календарных дней каждого ряда.
Ключи проверяются существующим `align_forecasts`: пропуски, лишние строки,
дубликаты и неконечные прогнозы вызывают ошибки. Отрицательные прогнозы
сохраняются без обрезки. Политика MAPE остаётся прежней.

### Тесты

Обычный `poetry run pytest` проверяет обвязку с подменой тяжёлого backend и
не запускает обучение. Реальный двухшаговый тест включается отдельно:

```powershell
$env:RUN_NBEATS_SMOKE = "1"
poetry run pytest tests/test_nbeats.py -k real_two_step_training
Remove-Item Env:RUN_NBEATS_SMOKE
```

Пробный запуск проверяет установку и форму результата, а не качество,
производительность на 913 000 строках или работу GPU. Seed фиксирован,
но побитовая воспроизводимость между разными версиями и устройствами не обещается.
Полное обучение на больших данных на этом этапе не выполняется.

## Реальные продажи: ограниченный эксперимент

Исходный `data/train.csv` доступен в репозитории исследования. Его копия сохранена
локально как `data/raw/train.csv`, рядом — `train.source.json` с commit, URL и SHA-256.
Оба файла исключены из Git правилом `/data/`. Сценарий не скачивает данные сам:
перед запуском нужен локальный CSV. Если файл происхождения присутствует,
SHA-256 проверяется до запуска моделей.

Проверены 913 000 строк: 10 магазинов × 50 товаров = 500 ежедневных рядов,
по 1826 наблюдений, даты 2013-01-01–2017-12-31. Validation: 2017-07-05–2017-10-02;
Test: 2017-10-03–2017-12-31. Результаты, версии, параметры и время приведены
в [отчёте эксперимента](docs/experiments/real_sales.md).

Измеренные метрики на Validation:

| Область оценки | Модель | MAE | RMSE | MAPE, % |
| --- | --- | --- | --- | --- |
| Все 500 рядов | Seasonal Naive (7) | 11,592 | 15,179 | 20,259 |
| Только `1/1`, `1/2`, `1/3` | Seasonal Naive (7) | 8,259 | 11,087 | 22,529 |
| Те же три ряда | N-BEATS, 5 шагов | 7,673 | 10,337 | 17,835 |

Baseline pipeline на всей панели занял 20,85 с; обучение N-BEATS на трёх рядах —
1,72 с (без создания модели и импортов). Результаты трёх рядов не оценивают
качество N-BEATS на всём датасете; Test не использовался для выбора модели.

```powershell
poetry run python -m sales_forecasting.real_data_experiment data/raw/train.csv --unique-ids 1/1 1/2 1/3 --max-steps 5 --report docs/experiments/real_sales.md
```

Сценарий сначала запускает существующий baseline pipeline на всех рядах.
Затем сравнивает baseline и N-BEATS только на явно выбранных 3–5 рядах, наследуя
те же Train и Validation из полного разделения. Выбирать ряды нужно до запуска,
без просмотра метрик. Число шагов ограничено диапазоном 2–20 (по умолчанию 5).
Используется основная архитектура Nixtla и конфигурация эксперимента с изменением
только `max_steps`; основной `EXPERIMENT_CONFIG` не меняется. Вычисления идут на CPU.
Результаты выводятся как JSON и записываются в Markdown; указанный отчёт при
повторном запуске перезаписывается. CSV и веса модели не сохраняются в Git.

Результаты baseline на всей панели и сравнения на трёх рядах показаны отдельно.
Ограниченный запуск N-BEATS не является оценкой качества на всех 500 рядах и
не доказывает сходимость модели. Выполнен один запуск без подбора параметров;
Test не передаётся обучению или оценщику, его неизменность проверяется отпечатком.
Обычные pytest-тесты сценария используют синтетические таблицы и подмену модели:
реальные CSV и обучение при каждом запуске тестов не требуются.
